# 백엔드 계약과 화면의 차이

정책 변경이나 신규 API 구현 요청서가 아니라 시안·프런트 구현 전에 확인할 목록이다. 기존 문서는 수정하지 않는다.

| 항목 | 확인한 사실 | 설계·다음 처리 |
|---|---|---|
| 서비스와 개인 블로그 | PRD는 여러 USER의 콘텐츠 공유 서비스다. 현재 초안의 서비스 목록에도 개인 공간 표현이 섞여 있다. | 공개 탐색·특정 블로그·본인 관리를 분리해 시안을 다시 구성한다. |
| 프로젝트 상태 | API/Domain은 IN_PROGRESS·COMPLETED다. 참고 이미지에는 준비 중·계획 중이 있다. | 진행 중·완료만 사용한다. |
| 공개 블로그 기본 정보 | 현재 Member 공개 Controller에는 handle로 블로그 기본 정보만 조회하는 endpoint가 없다. 글 응답의 author에는 정보가 있지만 빈 블로그에는 글이 없다. | 빈 블로그의 이름·작성자·회원 ID를 임의로 추측하지 않는다. 공개 블로그 메타데이터 계약 필요 여부를 별도 검토한다. |
| handle와 개인 Project/Board | Post는 handle 조회를 지원하지만 개인 Project/Board 목록은 memberId를 요구한다. | handle→memberId를 안정적으로 얻는 계약을 공개 블로그 정보와 함께 검토한다. 아직 새 API가 있다고 문서화하지 않는다. |
| 공개 Post 주소 | 백엔드는 handle + slug/글 번호를 공개 주소로 정의한다. 초안은 `/posts/{id}` 링크를 주로 사용한다. | 최종 공개 링크·canonical·내부 조회 경로를 일치시킨다. |
| Category·Tag·Board | 공통 주제, 기술 태그, 개인 최대 3단계 게시판은 별개다. 초안은 Tag 중심 탐색만 있다. | 별도 탐색·편집과 연결 관계를 설계한다. |
| 소개·연락처 | 현재 Member DTO에 자기소개·메일·SNS·GitHub 필드는 없다. | 서비스 소개와 개인 소개를 구분한다. 참고 이미지의 연락처 아이콘을 가짜 링크로 구현하지 않는다. |
| 집계·아카이브 | 페이지 응답에는 totalElements가 있지만 제공되지 않는 월별 통계·계획 중 상태 수는 없다. | 현재 제공되는 범위로만 표시하고 월별 집계 API를 있다고 가정하지 않는다. |
| 미디어 조회 | Project 목록 DTO에는 media가 없고 상세에 포함된다. URL은 15분 만료·권한에 따라 null이다. | 목록 썸네일이 필요하면 계약 추가 여부를 별도 검토한다. 목록마다 상세를 호출하는 우회와 URL 저장은 기본으로 삼지 않는다. |
| 인증된 브라우저 검증 | 초안의 API 모의 테스트·빌드는 통과했지만 실제 USER 로그인·미디어 처리 검증은 남아 있다. | callback 등록·Origin을 맞춘 후 실제 사용자 흐름에서 확인한다. |
| 문서 구현 상태 표기 | PRD 5.2의 일부 “후속”·관리자 미구현 표기와 API/HANDOFF의 완료 기록이 다르다. | 제품 정책은 PRD, 구체적 계약·완료 상태는 API·코드·HANDOFF를 함께 대조한다. 충돌한 표기를 새 정책의 근거로 삼지 않는다. 기존 PRD는 변경하지 않는다. |

## 구현 범위 구분

현재 초안에는 로그인·프로필·공개 목록/검색/상세·미디어 관리와 좋아요 연결 코드가 있다. 개인 블로그·Board·전체 작성/편집·댓글·탈퇴·관리자 화면과 모든 상태의 실제 연동이 완료된 것은 아니다. 시안은 MVP 목표를 다루되 구현 완료 상태와 분리한다.

## 우선 확인

1. 공개 탐색, 개인 블로그, 내 관리 화면을 구분한 대표 시안을 검토한다.
2. 공개 블로그 기본 정보·handle 식별 계약과 Project 목록의 이미지 필요 여부를 정한다.
3. 필요하면 백엔드에 별도 목적·완료 조건을 가진 작업을 제안한다. 프런트 구현 중 임의로 endpoint나 필드를 추가하지 않는다.
4. 합의한 화면 단위로 구현·계약 테스트·브라우저 검증을 진행한다.
