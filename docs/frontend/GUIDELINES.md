# 프런트엔드 작업 규칙

## 1. 문서 기준

백엔드 PRD·API·SECURITY·DB는 제품·계약·보안·저장 정책의 기준이다. 이 폴더의 SCREEN_SPEC은 화면 요구사항, DESIGN은 시각·상호작용 기준이다. 문서와 코드가 다르면 근거와 영향을 CONTRACT_GAPS에 기록하고 정책을 임의로 정하지 않는다.

기존 문서를 이 문서에 복사해 별도의 제품 정책으로 만들지 않는다. 실제 API가 제공하는 필드·역할·상태만 사용한다. 기존 파일과 사용자 변경은 보존한다.

## 2. 구현 전 확인

- 기능의 목적, 화면, 접근 가능한 역할, API, 입력·실패·빈 상태와 완료 조건을 확인한다.
- 초안과 최종 시안을 구분한다. 참고 이미지의 메뉴·수치·상태·연락처를 실제 기능으로 간주하지 않는다.
- 설치된 Next.js의 `node_modules/next/dist/docs/`에서 해당 기능의 지침을 확인한다. 자동 생성된 루트 AGENTS의 프레임워크 안내는 유지한다.
- 새 의존성은 기존 도구로 해결되지 않는 이유가 있을 때만 추가한다. 주 모델·추론 설정은 사용자 선택을 따른다.

## 3. 코드 책임

현재 Next.js·React·TypeScript와 기존 패턴을 따른다. 라우트 조립은 `src/app`, 재사용 화면은 `src/components`, HTTP·계약 타입은 `src/lib`에서 시작한다. 기능이 커지면 auth·post·project·member·admin 책임으로 묶고 매 기능마다 추상화 계층을 복제하지 않는다.

상태·Effect·이벤트·브라우저 API가 필요한 부분만 Client Component로 둔다. 서버 전용 비밀이나 로직을 클라이언트에 전달하지 않는다. 타입의 `any`, 실패를 숨기는 임의 캐스팅과 HTML 직접 삽입을 피한다. 사용자 콘텐츠는 기본 React 이스케이프를 사용한다.

회원·콘텐츠 ID는 문자열로 유지한다. 페이지 요청은 0부터, 화면 번호는 1부터 표시한다. API URL·DTO·오류 코드는 공통 HTTP 계층과 계약 타입을 재사용한다. TSID를 Number로 바꾸지 않는다.

## 4. 인증·보안

- USER는 Naver 로그인, 관리자는 별도 관리자 로그인·세션을 사용한다.
- Access JWT는 메모리에서만 보관한다. localStorage·sessionStorage·URL·로그에 토큰을 남기지 않는다.
- Refresh Token은 백엔드 HttpOnly Cookie를 사용한다. 기존 Secure·SameSite·Origin·CORS·CSRF 정책을 유지한다.
- Refresh는 한 탭에서 진행 중 요청을 공유한다. 일회용 OAuth code와 Refresh 실패를 자동 재시도하지 않는다. StrictMode의 중복 Effect를 검증한다.
- 권한 검사는 서버가 최종 결정한다. UI의 버튼 숨김만으로 보안을 보장한다고 설명하지 않는다.
- OAuth callback의 code·state를 처리 후 주소에서 제거하고 외부 URL·업로드 파일·사용자 입력을 검증한다.
- `NEXT_PUBLIC_*`에는 공개 설정만 둔다. 실제 .env·JWT 키·R2 credential·Naver Secret은 읽거나 복사·커밋·출력하지 않는다. 별도 사용자 허용이 있으면 그 범위만 적용한다.

## 5. 화면 품질

화면마다 로딩·빈 목록·입력 오류·연결 실패·권한 거부·처리 성공 상태를 구현한다. 실패하면 예시 콘텐츠로 대체하지 않는다. 미리보기 데이터에는 예시임을 명시한다.

키보드 탐색, 연결된 label, 보이는 focus, 메뉴 Escape·포커스 복귀, 숨겨진 메뉴의 비활성화, 이미지 대체 텍스트를 확인한다. 모바일에서 내용·버튼이 잘리거나 글자가 세로로 좁아지지 않아야 한다. 테마·사이드바 선택은 화면 이동에도 일관되게 유지한다.

## 6. 검증

기본 명령은 `npm run typecheck`, `npm test`, `npm run build`다. 동작 변경에 관련 검증을 추가하고 성공한 동일 검증을 이유 없이 반복하지 않는다.

모의 API 테스트·실제 백엔드 연결·실제 OAuth·브라우저 검증을 구분한다. 인증 회전·로그아웃 경합, 검색 응답 경합, 페이지 경계, 공개/소유자 UI를 확인한다. 시각 변경은 데스크톱·모바일과 실제 렌더링을 확인하고 결과·남은 문제를 기록한다.

## 7. Git 작업

프런트엔드는 별도 저장소로 관리할 것을 목표로 한다. 현재 원격 저장소와 Issue 체계는 연결되지 않았다. 연결 전에는 백엔드 저장소에 프런트 작업을 임의로 push하거나 가짜 Issue 번호를 사용하지 않는다.

저장소 연결 후 dev에서 작업 브랜치를 분기하고 dev 대상 PR로 통합한다. main은 릴리스용이다. 브랜치는 `feature/<이슈번호>-<요약>`, `fix/`, `docs/`, `chore/` 규칙을 사용하며 개발 도구·에이전트 이름을 접두사로 사용하지 않는다. 사용자에게 이미 허용받은 범위에서 Commit·push·PR을 진행한다.

## 8. 완료 기준

화면이 보이는 것만으로 API 연동 완료라고 하지 않는다. 계약·권한·입력·오류·반응형을 확인하고 완료 범위·검증 결과·미확인 사항·다음 작업을 짧게 인계한다.
